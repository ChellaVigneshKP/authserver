# Hosted account forms security addendum

Date: 24 October 2026. Status: **approved in chat 2026-10-24; implement through the existing SDD workflow**.

This amends only the hosted profile/password part of the approved identity portal design. The portal, enterprise visual direction, other features, and implementation plans remain approved. The user approved this reviewed addendum in chat on 2026-10-24.

## Problem and intent

The real separate-host browser test proved two existing dependencies fail: the issuer's host-only SameSite=Strict SSO cookie is omitted on the first cross-site navigation, and a subsequent issuer-origin navigation fails the original client-origin fingerprint. More importantly, SingleSignOnService.createTokenResponse returns the management OAuth access token and signing_key; auth-forms.js retrieves them and inserts the token into the hosted form. Making that legacy flow work would expose the BFF-held management credentials to the browser, violating the approved server-held-token boundary.

Account profile/password changes must work through issuer-hosted pages without exposing OAuth tokens, management signing keys or client secrets. Recovery delivery remains separately dependent on configured providers; this addendum does not claim or implement external delivery.

## Recommendation and alternatives

Add dedicated issuer-hosted account forms authenticated by the existing Strict SSO session, current SQL identity, fingerprint continuity, Spring CSRF and a short-lived single-use form nonce. TLS supplies request confidentiality/integrity outside explicit loopback development. These additive forms use session/CSRF/nonce proof rather than the legacy browser-held OAuth/HMAC proof. This is an explicit change to the earlier requirement to reuse that proof flow.

Leaving the links unavailable would preserve privacy but fail the intended account portal. Enabling the old SSO token response would violate privacy. New browser cryptography, WebAuthn enrollment and a Next.js credential proxy add unnecessary scope and are excluded.

## Routes and trust boundaries

- GET `/portal/account-action`: issuer-rendered transition with a closed profile/password action, public client ID and bounded return target. Validate an active registered WEB client, its exact portal `/auth/callback` registration, and only that callback origin plus `/account` or `/account/security` as return destinations. No arbitrary URL, script redirect, token, secret, form mutation or new login grant. A manual same-origin Continue link establishes an issuer navigation context while retaining Strict cookie policy. Missing SSO on this first transition never authenticates anyone.
- GET/POST `/portal/account/profile` and `/portal/account/password`: additive issuer-only forms. Existing `/user/change-*`, `/oauth2/sso`, management APIs, BFF token storage and global fingerprint rules remain unchanged. Do not add the new routes to CSRF exclusions.
- Authenticate from the existing SSO cookie and current active auth session and SQL human identity. Verify session/subject/client agreement, active client and registered callback. The launch includes a public expected login/subject GUID from the authenticated portal session; Java compares it to the authenticated SSO identity and rejects a mismatch before displaying personal data or allowing a write. This identifier narrows the permitted identity and grants no authority; it is never trusted as authentication. The issuer form clearly identifies the authenticated account. POST derives the mutation target solely from the verified SSO/nonce binding, never a posted user ID. A user who intentionally edits a URL still cannot act on any identity without its matching SSO session. No new management token is issued or returned. Inactive or ambiguous identity fails closed.
- A dedicated hosted-flow fingerprint helper may canonicalize an **exact configured issuer origin** Referer to the authenticated session's verified registered callback origin for these exact new form routes only. Compare the original fingerprint with actual User-Agent and language, retaining the original request-date offset contract: F1 and the new form script use UTC ISO timestamps, including in non-UTC browsers. Reject an altered offset; do not claim this detects changes to the browser timezone, and do not change F1 to use local offsets. Trust AuthorizationServerSettings, not Host/forwarded headers or caller-selected origins. Missing, malformed or foreign Referer, invalid cookie/session, unregistered callback, mismatched browser properties and mixed/foreign continuation fail closed. `/oauth2/sso` gets no issuer-origin exception.
- POST requires existing Spring CSRF plus exact configured issuer Origin checks and the form nonce. Existing HMAC APIs and legacy form checks are not disabled. Form data goes only to Java; Next.js collects no password and performs no credential proxying.

## Nonce lifecycle and mutations

GET creates a cryptographically random 256-bit nonce with a maximum five-minute TTL. Store its server-side record in a dedicated Redis namespace, bound to the browser HttpSession, auth session, subject, client, exact form action and safe return target. It grants no authority without the matching current SSO session and CSRF token. Render only this form nonce and the existing CSRF value; neither OAuth tokens nor signing keys appear in HTML, network JSON, URLs, browser storage, logs or screenshots. A nonce is an explicitly allowed transient hidden form proof, not a management credential.

Allow at most one outstanding nonce for each profile/password action in a browser HttpSession; a new GET replaces the previous nonce for that action, so an older editing tab must reopen the form. Bound input sizes to the existing DTO limits and use atomic compare-and-consume so a mismatched nonce cannot destroy a valid record. POST verifies current session/identity, Origin, fingerprint, CSRF, action, expiry and binding before any mutation. Only one POST can consume a nonce. A replay or expired/cross-session/cross-action nonce cannot mutate data. Validation failure and uncertain transport results require a fresh GET/nonce; no automatic write replay. Redis failure fails closed with an actionable unavailable state. Never store plaintext form fields, passwords or a reusable password-derived verifier in the nonce record. User-entered passwords go only to the Java TLS POST; do not repopulate them after a validation failure or include them in model errors, responses or logs.

These new forms support local identities only. Provider-SYNC identities receive a clear provider-managed-account/unavailable message and cannot mutate through these routes; recheck mode on POST as well as GET. Do not call external profile/password synchronization from this flow or silently fall back to a local write. Legacy provider routes remain unchanged. Enabling provider-managed self-service requires a separately qualified provider-success/revocation-failure design; no such environment is available now.

Reuse the existing local domain validation/mutation pipeline: profile DTO/view validation, phone normalization and UserService.updateForChangeProfilePage; password old-password verification, policy/history validation and UserService.updatePassword. Preserve local/provider synchronization distinctions. Password change on these new forms deliberately improves the examined legacy behavior: after the successful password write, revoke all Java authentication sessions, SSO sessions and access/refresh tokens for the affected login identity, including the current session, across clients. Require sign-in again. The portal deletes its own Redis record when the ensuing Java401 is confirmed, following its existing invalid-bearer path; do not trust an unsigned success query to perform another user's logout. Profile changes preserve existing session behavior. Do not silently change the legacy password route's behavior as part of this additive path. Make local password update plus SQL session/token/authorization revocation atomic in the shared primary DataSource transaction; the builder check verified this is feasible in the existing repositories. Clear current issuer session/cookies after commit. Current token/session reads go to SQL; verify old credentials and all previously issued tokens are rejected after the transaction. No new role/organization privilege, identity reassignment or self-elevation is introduced. Any extracted shared helper preserves legacy behavior.

After a proven server-side profile result, return through the bounded registered portal continuation to a clean account/security URL. After a password change, render a Java-hosted confirmation requiring sign-in again, clear the current issuer authentication cookie/session, and offer only the validated portal return/sign-in navigation; the next portal context request confirms token revocation and clears its BFF record. Unsigned callback query data alone never proves a save succeeded. Cancellation returns safely without a mutation; it must not weaken legacy authorization-code callback handling.

## Verification and limits

Approval was received in chat on 2026-10-24. Amend F2's plan/brief with exact interfaces and tests and execute through SDD.

Required evidence includes CSRF/Origin rejection; missing/invalid/inactive SSO and identity; unknown client/callback/foreign continuation; altered UA/language/offset/Referer; missing/expired/replayed/cross-session/cross-action nonce; concurrent consume; bounded Redis outage; validation/history/provider failure; cancellation with unchanged SQL. Use real browser profile and password POSTs on separate portal/issuer hosts in a non-UTC timezone with checks enabled. Verify SQL state, new-password login and old-password rejection, all affected login sessions/token revocation and forced reauthentication, portal-session cleanup on confirmed401, safe return, and absence of OAuth/key material in DOM/network/storage/logs. Preserve legacy HMAC and ordinary API regressions and run the full backend gate once final Java changes settle.

This does not qualify production deployment, genuine provider delivery/MFA, recovery success, or every legacy hosted client. The extra Continue step is a visible cost for cross-site navigation, and the additive forms introduce a second authentication/proof path that needs focused security review. Final complete-screen visual acceptance remains a later gate.

## Calls proposed by the agent for approval

- Password change signs the affected login out everywhere; this intentionally tightens the additive route compared with the examined legacy path. Profile changes retain existing behavior.
- An SSO/portal identity mismatch is rejected, with clear issuer-account labeling; no new cross-account chooser or delegated authority is introduced.
- UTC fingerprint offset continuity is preserved; changing local browser timezone is not claimed to be detected.
- One outstanding nonce per action means opening another copy of the same form expires the earlier form.
- Provider-SYNC accounts cannot mutate through these new forms until their external consistency/recovery flow is separately designed and qualified; legacy routes stay unchanged.

These recommendations were included in the addendum approved by the user on 2026-10-24. The independent builder check raised the first three topics; this text now settles the proposed behavior explicitly.

Builder follow-up identified the external-provider transaction boundary. The proposed resolution is explicit fail-closed exclusion of provider-SYNC writes on these additive routes; local password/revocation is a single SQL transaction.

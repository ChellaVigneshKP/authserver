## Global Constraints

- Existing `/user/change-*`, `/oauth2/sso`, management APIs, BFF token storage and global fingerprint rules remain unchanged. Do not add the new routes to CSRF exclusions.
- These new forms support local identities only. Provider-SYNC identities receive a clear provider-managed-account/unavailable message and cannot mutate through these routes; recheck mode on POST as well as GET.
- GET creates a cryptographically random 256-bit nonce with a maximum five-minute TTL.
- Allow at most one outstanding nonce for each profile/password action in a browser HttpSession; a new GET replaces the previous nonce for that action, so an older editing tab must reopen the form.
- Form data goes only to Java; Next.js collects no password and performs no credential proxying.
- A nonce is an explicitly allowed transient hidden form proof, not a management credential. OAuth/access/refresh/ID tokens and management signing keys never enter these forms, browser JSON/HTML/storage/URLs/logs/screenshots.
- Make local password update plus SQL session/token/authorization revocation atomic in the shared primary DataSource transaction. Require sign-in again and clear issuer cookie/session only after commit.
- Preserve all database records and V1–V14 checksums; no shared reset/restart, security toggle weakening, arbitrary URL proxy, external provider write or automatic write replay.

## Review Focus

- Portal account A with issuer SSO B must reject before rendering personal details or changing either account (access-policy and real-browser tests).
- Wrong/replayed/concurrently submitted form nonce must not consume another valid form or duplicate a write (Redis compare-and-consume and HTTP/SQL tests).
- Same username under a different branding, unrelated user and machine grants must survive affected-login password revocation (SQL/real-introspection tests).
- A failure while revoking authorizations must roll back the password write; an in-flight old-password authorization must not escape required revocation (transaction and coordinated grant tests).
- Validation errors, password reauthentication and Redis failure must not leak passwords/tokens/keys or report a save that did not commit (privacy/error/browser tests).

## File map and interfaces

Use `J=src/main/java/com/chellavignesh/authserver`, `T=src/test/java/com/chellavignesh/authserver` below as exact prefixes, not literal directories.

Create a focused `J/adminportal/hosted/` feature:
- `HostedAccountAction.java`: closed PROFILE/PASSWORD wire values `profile`/`password`.
- `HostedAccountAccessPolicy.java`: strict launch validation and active SSO/current SQL local identity/fingerprint checks; consumes existing SingleSignOnService/Repository, AuthSessionService, ApplicationService, AuthorizationServerSettings and current-user queries.
- `HostedAccountActor.java`: server-only resolved auth session, stable credential login GUID, profile/member GUID, branding, registered callback URI and exact return URI. No model/log exposure of this record.
- `HostedAccountNonceStore.java`: Redis issue/atomic compare-consume of session/action-bound proof; injectable Clock/SecureRandom.
- `HostedAccountMutationService.java`: local profile validation/update and transactional password/revocation; shared SQL management lock before fresh mutable identity/credential checks.
- `HostedAccountRevocationRepository.java`: parameterized primary-DataSource revocation scoped by stable credential GUID and its canonical username/branding, including Java auth sessions/SSO/access-refresh/auth-code state and correlated Spring grants. AuthSession.SubjectId is the username, not the login GUID: resolve the locked canonical credential username and ExternalSource.SourceCode for that stable credential (UQ_Credential_Username_Source), retain branding and human grant correlation, and reject ambiguity. Never delete grants by username alone.
- `HostedAccountController.java`: GET transition, exact GET/POST form endpoints, safe errors/cancel/confirmation and size/type limits; keep rendering separate from mutation/repository work.

Create `src/main/resources/templates/pages/portal/account-{transition,profile,password,confirmation,error}.html` and `src/main/resources/static/js/hosted-account.js`. Use existing issuer branding primitives without the legacy auth-forms.js token fetch. JS only generates UTC timestamp/normal form behavior and Base64 password wire values for the existing ChangePasswordDtoValidator. Base64 is encoding, not confidentiality; TLS is required outside explicit loopback development. Never repopulate password fields or render rejected password values.

Modify `J/security/SpringSecurityConfig.java` only to admit the three exact additive paths to controller-based SSO enforcement and retain Spring CSRF on both POSTs; no blanket `/portal/**` permit/ignore rule. If a scoped pre-binding body-limit filter is needed, confine it to these two form POSTs, with 64KiB total/controlled urlencoded fields and safe413. Original API filters are untouched. Add a dedicated fingerprint overload/helper only for the new form policy; global callers retain existing behavior.

Interfaces to implement (names may use existing compatible domain types where noted):
- `HostedAccountAccessPolicy.validateLaunch(String action,String clientId,UUID expectedLoginId,URI returnTo):ValidatedLaunch`; validate active WEB client and exact registered `/auth/callback` origin, exact `/account` or `/account/security` return, no credentials/fragment/unexpected query/duplicate values, bounded input.
- `HostedAccountAccessPolicy.requireActor(HttpServletRequest request,ValidatedLaunch launch,String requestDatetime):HostedAccountActor`; resolve cookie/current identity, compare stable expected credential GUID and client, require an IDP/local external-source type with both credential/profile sync flags explicitly false (unknown or either synchronized flag fails closed on both forms), and preserve UA/language/UTC-offset fingerprint against trusted callback origin only for an exact configured-issuer Referer. No SSO token endpoint exception.
- `HostedAccountNonceStore.issue(String httpSessionId,HostedAccountActor actor,HostedAccountAction action,URI returnTo):String` and `consume(String httpSessionId,HostedAccountActor actor,HostedAccountAction action,URI returnTo,String nonce):void`; five-minute TTL, one active slot/action, compare-and-consume atomically, safe typed503 on bounded Redis failure. Use the configured spring.session.redis.namespace plus a hosted-account suffix so owned test cleanup remains exact; preserve configured DB/endpoint selection. Bound complete Redis operations to the existing two-second limit and verify unavailable/stalled service behavior, without global Redis policy changes or uncertain-write retries. Store bindings/hash/expiry only, not form data.
- `HostedAccountMutationService.updateProfile(HostedAccountActor actor,ChangeProfileDto dto):void` and `changePasswordAndRevoke(HostedAccountActor actor,ChangePasswordDto wireDto):void`; validate/resolve fresh actor under transaction lock, apply existing local validators/phone normalization/current-password/history checks, derive target solely from actor; no posted subject or supplied branding authority.
- `HostedAccountRevocationRepository.revokeAllForLogin(UUID loginId):void`; all clients for that credential, source/branding-aware and human-only; use Spring authorization attribute correlation `JdbcOAuth2AuthorizationService.SESSION_ID`, not an unscoped principal-name delete. Follow existing SQL enum/state semantics. No migration is expected; if necessary only the next additive migration is allowed and requires upgrade preservation evidence.
- Extend `web/src/server/hosted-actions.ts` to `buildHostedAction(action,returnTo,expectedLoginId)` with stable public `PortalContext.subject.loginId`, not `PortalSession.subjectId` (JWT/SSO subject may be username). Emit issuer transition parameters only: closed action, configured public clientId, exact expected login GUID, exact absolute return URI and UTC datetime. Recovery keeps its existing separately unqualified route. Update `web/src/app/account/action/route.ts` to obtain fresh session/context and pass the stable public login ID; no credential input or token response.
